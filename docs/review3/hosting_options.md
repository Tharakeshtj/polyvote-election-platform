# Free permanent hosting options for PolyVote

Researched 2026-10-23. Every fact below was read from the platform's own pricing or docs page (URL given) unless marked **third-party** (a blog or forum, weaker evidence) or **not verified** (no source read in this session). Free tiers change often; re-check the linked page before relying on any number.

## What the app needs (from the repo)

- Python 3.12, FastAPI, started with `python -m uvicorn server:app --host 0.0.0.0 --port $PORT`.
- The React app is served from `frontend/dist`. **`frontend/dist/` is git-ignored** (`.gitignore`, `frontend/.gitignore`), so it does not exist on GitHub. The existing `Dockerfile` already builds it (Node 20 stage, then Python 3.12-slim stage), so a Docker deploy needs no extra step.
- SQLite files are created at runtime; `HOSTED_DEMO=true` (set in the Dockerfile) seeds a demo election when the database is empty (`hosted_demo.py`), so an ephemeral disk is fine.
- Optional: MongoDB Atlas via `MONGO_URI` (outbound 27017 or SRV DNS), optional Gmail SMTP on 587. The Dockerfile also sets `OTP_REQUIRED=true` and `OTP_DEMO_HINT=true`, which shows the one-time code on screen, so a blocked SMTP port does not stop evaluators from voting.
- **Before any deploy:** `Dockerfile`, `hosted_demo.py`, `requirements-hosted.txt` and `verification/` are currently untracked in git, and `server.py`, `election_core.py`, `audit_ledger.py` and several frontend files have uncommitted changes. Commit and push them to `main` of `Tharakeshtj/polyvote-election-platform`, otherwise the platform builds the old code.

## 2. Recommendation: Render, Free web service, Docker runtime

Why: it is the only candidate where the official docs state a permanent free web service, no payment required, deploy from GitHub with our existing Dockerfile, and no inactivity deletion described. Its drawbacks (sleep, ephemeral disk, blocked SMTP) are all handled by the app's existing hosted-demo mode.

### Deploy steps (browser and GitHub login only)

0. **Push the code.** On the laptop, commit and push everything the Docker build needs (`Dockerfile`, `hosted_demo.py`, `requirements-hosted.txt`, `verification/`, and the modified files) to branch `main` of `Tharakeshtj/polyvote-election-platform`. The repo must stay public. Do not commit `.env`.
1. Go to https://render.com and choose **Get Started / Sign up**, then **Sign up with GitHub** and authorize Render.
2. In the dashboard (top right) click **New +**, then **Web Service**. Choose **Build and deploy from a Git repository** (public repo tab).
3. Pick `Tharakeshtj/polyvote-election-platform` and click **Connect** (if the repo is not listed, click "Configure account" and grant Render access to that repo).
4. Fill in the form:
   - **Name:** `polyvote` (the URL becomes `https://polyvote.onrender.com`; if the name is taken Render appends a suffix, so read the actual URL on the service page).
   - **Language:** **Docker** (Render docs: set the Language field to Docker even for a Python app).
   - **Branch:** `main`. **Root Directory:** leave blank. **Dockerfile Path:** `./Dockerfile` (default).
   - **Region:** choose the one closest to the evaluators; the Atlas cluster (if used) is better in a nearby region.
   - **Instance type / Compute:** **Free**.
   - **Build Command:** not used with Docker. **Docker Command / Start Command:** leave **blank**; Render then runs the Dockerfile's `CMD`, which is already `python -m uvicorn server:app --host 0.0.0.0 --port ${PORT:-8000}`. (If you prefer to set it explicitly, put `sh -c "python -m uvicorn server:app --host 0.0.0.0 --port $PORT"` in Advanced, Docker Command.)
5. Under **Environment Variables** (build and runtime) add:
   - `ADMIN_PASSWORD` = a strong password of your choice (the admin console password).
   - `LEDGER_KEY` = a long random string (keyed ledger chain). Generate with `python -c "import secrets; print(secrets.token_hex(32))"`.
   - `OTP_SECRET` = a long random string (read in `verification/otp.py`; if unset a random one is generated at each start, which is acceptable for the demo; it is not listed in `.env.example`).
   - `PUBLIC_URL` = leave empty on the first deploy; after you see the real URL, set it to `https://<name>.onrender.com` so the voter-page QR code points at the public link.
   - `MONGO_URI` = **optional, see limitation 5 before setting it**.
   - Do **not** set `SMTP_USER` / `SMTP_PASS` (SMTP is blocked on Free, see below). The Dockerfile already sets `HOSTED_DEMO=true`, `OTP_REQUIRED=true`, `OTP_DEMO_HINT=true`; do not override them.
   - `PORT` need not be set (Render defaults it to 10000 and the Dockerfile reads `$PORT`).
6. Click **Deploy Web Service** (or **Create Web Service**). Watch the **Deploys** log; the first build compiles the React app and takes several minutes. Status turns **Live** when the app answers on the port.
7. Open the `onrender.com` URL shown at the top of the service page. Expect the first load to take about a minute if the service was asleep.
8. (Recommended) In **Settings, Auto-Deploy** keep it on, so a `git push` to `main` redeploys. Share the URL with evaluators and mention the cold start.

If Docker build fails or is too slow, the native alternative is Language **Python 3**, Build Command `pip install -r requirements-hosted.txt`, Start Command `python -m uvicorn server:app --host 0.0.0.0 --port $PORT`, plus `HOSTED_DEMO=true`, `OTP_REQUIRED=true`, `OTP_DEMO_HINT=true` as env vars. This only works if `frontend/dist` is committed (it is git-ignored now), so Docker is the safer choice. Python version for native deploys is set with `PYTHON_VERSION` (full version, e.g. `3.12.8`) or a `.python-version` file; the current default for new services is 3.14.8 (https://render.com/docs/python-version).

## 3. Limitations of the recommendation (Render Free)

1. **Sleep and cold start.** Spins down after 15 minutes without inbound traffic; the next request takes about one minute and shows a loading page. Tell evaluators to wait, or open the link a minute before a demo. An external uptime pinger could keep it awake, but whether Render allows or counts that was **not verified** (a pinger every 10 minutes would use about 744 of the 750 free hours).
2. **Data reset.** The filesystem is ephemeral; SQLite files are lost on every redeploy, restart and spin-down, so each wake-up is a fresh database. `hosted_demo.seed_if_empty()` re-creates the demo election (30 voters, 18 pre-cast ballots) at start. Anything an evaluator creates (new elections, votes) can disappear after idle. Render may also restart a free service at any time.
3. **SMTP is blocked.** Render docs: outbound ports 25, 465 and 587 are blocked on Free web services, so Gmail SMTP on 587 will fail (the app logs the failure and does not block sign-in). The one-time code is shown on screen via `OTP_DEMO_HINT=true`, and the admin Mail outbox shows every code. Real email would need a paid Render instance or an HTTPS email API (e.g. SendGrid, Mailgun; Render support advises this) which means a code change and a separate provider's free-tier terms (**not verified**).
4. **MongoDB Atlas reachability.** Only 25/465/587 are documented as blocked, so port 27017 / `mongodb+srv` should be reachable, but I did not test it. Atlas's IP access list must allow Render. Render's outbound IPs are shared per-region ranges (dashboard: service, Connect, Outbound tab), and the Atlas "Allow access from anywhere" (0.0.0.0/0) entry is the practical way to handle that on a free M0 cluster (this Atlas option was **not verified** from MongoDB's page, which did not load that section). Treat the Atlas credentials as the security boundary.
5. **Atlas and demo reseeding interact.** `hosted_demo.seed_if_empty()` calls `clear_ledger()` before reseeding, which per its docstring clears the ledger so the ledger and the database start together. If `MONGO_URI` is set, every cold start would therefore wipe the Atlas ledger collection. Either leave `MONGO_URI` unset on the public demo (the ledger then uses the local JSON file, also reset on restart), or point it at a throwaway demo database/collection, not your real data. This is from reading the code, not tested on Render.
6. **Hours and bandwidth.** 750 free instance hours per workspace per month, spun-down time does not count; if used up, free services are suspended until next month. Bandwidth and build-minute allowances exist and are enforced; the exact figures were not on the official page I read (a third-party page says 100 GB and 500 build minutes, **not verified**). Render may suspend a service with unusually high outbound traffic. Only one free instance per service, no persistent disk, no shell access.
7. **Card and account risk.** The docs say no payment is required, but older community threads report card prompts for verification; if asked, the fallback is Cloud Run or the laptop option.
8. **Permanence.** Docs describe no inactivity-based deletion for free web services, but "for at least a few months" is not a written guarantee; Render can change the free tier. Re-check the live URL weekly and before the evaluation.

## 4. Second choice: Google Cloud Run (needs a credit card for the billing account)

Choose this if Render refuses the account or a stable cold start is needed. It stays at $0 within the free quota (2M requests, 360,000 GiB-s, 180,000 vCPU-s, 1 GB North America egress per month) but requires a Cloud Billing account with a card, so set a budget alert.

1. Sign in at https://console.cloud.google.com, create a project, and link a billing account (card required; a free trial can provide it).
2. Open **Cloud Run, Create service, Continuously deploy from a repository (source or function)**. Click **Set up with Cloud Build**, authorize GitHub, pick `Tharakeshtj/polyvote-election-platform`, branch `main`. For build type choose **Dockerfile** and source location `/Dockerfile`. (Google's source-deploy page says a Dockerfile in the source directory is used for the build; the GitHub setup page recommends buildpacks, so confirm the Dockerfile option is selected. If the console enables APIs or asks for the Cloud Run Builder role, accept.)
3. Set **Region** (e.g. `us-central1`, free quota is stated for North America egress), **Authentication: Allow unauthenticated invocations**, **Billing: Request-based** (default), **Minimum instances: 0**, **Maximum instances: 1** (so all requests hit the same SQLite file), **Container port: leave default**; Cloud Run injects `PORT` (8080) and the Dockerfile CMD uses `${PORT}`.
4. Add the same environment variables as in section 2 (`ADMIN_PASSWORD`, `LEDGER_KEY`, `OTP_SECRET`, `PUBLIC_URL` set after first deploy).
5. Click **Create**. The URL has the form `https://<service>-<hash>.<region>.run.app`.

Limitations: filesystem is in-memory and lost when the instance stops (reseeding handles it); CPU is only allocated while a request is processed under request-based billing, so the background email thread may stall (OTP hint on screen covers this); SMTP 587 is documented as not blocked on Google Cloud (Compute Engine page; not verified for Cloud Run); outbound idle connections time out after 20 minutes; cold start duration not verified.

## Fallback: laptop + ngrok free static domain

Run `python -m uvicorn server:app --host 0.0.0.0 --port 8000` after `npm run build` in `frontend/`, then `ngrok http 8000 --url <your-assigned-domain>` (the free plan assigns one domain such as `name.ngrok-free.app`; exact command flag not verified against ngrok docs). Works with Atlas and Gmail SMTP from the home network, but only while the laptop is on, is capped at 1 GB and 20,000 requests per month, and shows an ngrok interstitial page on first visit (https://ngrok.com/docs/pricing-limits/free-plan-limits/). Use it for live demos and as a backup, not as the permanent link.
